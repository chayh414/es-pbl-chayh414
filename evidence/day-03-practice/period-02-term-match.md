# 2교시 실습 — term과 match

## (공통) 문제 1 — 제공 코드로 정확 조건 확인

```http
GET /products/_search
{
  "size": 5,
  "query": { "term": { "category": "전자기기" } }
}
```

### 결과 입력

- `hits.total.value`: 1250
- 상위 3개 문서 ID: P-00009, P-00025, P-00081
- 상위 3개 문서의 category: 전자기기, 전자기기, 전자기기
- 모든 확인 문서가 정확 조건을 만족하는가: 예 (5건 모두 category="전자기기")
- `term`을 선택한 mapping 근거: `category`는 mapping에서 `keyword` 타입이라 분석(형태소 분해)되지 않고 원본 문자열 그대로 저장된다. 따라서 "전자기기"라는 값과 완전히 동일한 문자열만 찾는 `term`이 적합하다. text였다면 분석기를 거치므로 term이 아니라 match를 써야 한다.

## (공통) 문제 2 — text 전문 검색 직접 구현

`products` index에서 상품명 `name`에 `무선`이라는 검색 의도가 있는 문서를 찾으세요. text 전문 검색에 적합한 query를 선택해 최대 5건을 반환하세요.

### API 전체 입력

```http
GET /products/_search
{
  "size": 5,
  "query": { "match": { "name": "무선" } }
}
```

### 결과 입력

- 선택한 query와 이유: `match`. `name`은 text 타입이라 색인 시 형태소 단위로 분석되어 저장되므로, 정확 매칭이 아니라 "무선"이라는 단어가 포함됐는지 분석 기반으로 찾는 `match`가 적합함
- `hits.total.value`: 505
- 상위 3개 ID·name: P-00025(MobiCore 컴팩트 무선 이어폰), P-00042(CleanMate 실속형 무선 청소기), P-00129(Auralis 스마트 무선 이어폰) — 3건 모두 name에 "무선" 포함 확인

## (공통) 문제 3 — 부적절한 조합 비교

같은 `name` field와 `무선` 검색어에 `term` query를 사용한 API를 직접 작성하세요. 문제 2와 결과를 비교하고, 차이를 mapping 또는 분석된 token 관점에서 설명하세요.

### API 전체 입력

```http
GET /products/_search
{
  "size": 5,
  "query": { "term": { "name": "무선" } }
}
```

### 비교 결과

- 문제 2 total / 문제 3 total: 505 / 505 (완전히 동일)
- 공통으로 나온 문서 ID: P-00025, P-00042, P-00129, P-00153, P-00209 (5건 전부 동일, score까지 동일)
- 달라진 이유: 이번 경우엔 달라지지 않았음. `name` field는 색인 시 분석기를 거쳐 "컴팩트 무선 이어폰" → `컴팩트`/`무선`/`이어폰` 같은 개별 토큰으로 쪼개져 저장된다. 검색어 "무선"이 한글 단일 단어라 대소문자 변환이나 형태소 축약이 필요 없어서, `match`가 내부적으로 만드는 분석된 토큰("무선")과 `term`이 찾는 원본 문자열("무선")이 우연히 정확히 같아졌다. 그래서 이번엔 두 query가 같은 결과를 냄.
- `term`은 text에서 항상 0건인가? 실제 근거: 아니오. 이번 결과가 그 증거다. `term`은 "검색어를 분석하지 않고 색인된 토큰과 원본 문자열을 그대로 비교"하는 것이지, text field 자체를 거부하는 게 아니다. 검색어가 대문자를 포함하거나("Wireless"), 여러 단어("무선 이어폰")이거나, 조사가 붙은 형태("무선을")였다면 색인된 개별 토큰과 정확히 일치하지 않아 0건이 나왔을 가능성이 높다. 즉 결과가 같거나 다른 건 "검색어가 분석된 토큰 형태와 우연히 일치하는가"에 달려 있다.
